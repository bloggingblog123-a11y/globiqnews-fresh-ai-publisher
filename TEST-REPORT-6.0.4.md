# Queue and RSS fix — 6.0.4

## Requested findings

1. **Exact queue cause:** released 6.0.3 had no persistent server-side category queue or completion dispatcher. Run All chained requests in the browser. Busy requests returned a lock error rather than preserving the request. Scheduled category continuations waited 75 seconds (90 seconds on a busy lock) and relied on WP-Cron being triggered. Releasing the lock did not dispatch a waiting category.
2. **Global lock:** `gnf5_article_worker` enforced a single article worker globally. It prevented unrelated categories from running simultaneously, but normal completion generally released it. A permanently retained healthy lock was not established as the primary bug. Version 6.0.4 uses up to two atomic slots and independent category locks, with ownership checks and stale-state reconciliation.
3. **Worker release:** normal old runs released the slot but there was no server-side queue to take it. New finalization records counters, final status and logs before releasing the category lock/slot and dispatching the next job. Terminal jobs with leftover slots are repaired.
4. **Cron dependency:** yes, old scheduled continuation unnecessarily deferred already-available work to cron. New normal handoff sends a nonblocking same-site HTTP worker request immediately. Deduplicated immediate cron events and a one-minute watchdog provide fallback, subject to WordPress cron actually being triggered.
5. **Early returns:** the old no-sources return released its lock explicitly but bypassed common run finalization; no normal or early path handed off to a queued category. Acquired-lock processing now has `try/finally`; queue exceptions and shutdown cleanup also finalize/release. Invalid or replayed worker requests never acquire a new slot. Fatal process termination beyond PHP shutdown requires the stale-lock watchdog.
6. **Files:** runtime changes are `globiqnews-fresh-ai-publisher.php`, `assets/admin.js`, `includes/class-gnf6-queue.php` (new), `includes/class-gnf5-utils.php`, `includes/class-gnf5-runner.php`, `includes/class-gnf5-sources.php`, `includes/class-gnf5-topics.php`, and `includes/class-gnf5-admin.php`. Version/release docs: `readme.txt`, `README.md`, `CHANGELOG.txt`, `RELEASE-NOTES.md`, this report. Tests: `tools/tests/test-queue604.php`, `tools/tests/test-admin604.cjs`, updated `tools/tests/test-admin601.cjs`.
7. **Central dispatcher:** `GNF6_Queue::dispatch_available_category_workers()`. Per-category job CAS claims, atomic category/worker locks and per-dispatch tokens prevent two requests claiming the same category. Called after enqueue, worker completion/release, stale recovery and eligible source retry; cron fallback uses the same path. Ineligible scheduled jobs are skipped before acquiring a slot.
8. **Tests:** 47 new queue/RSS checks plus 298 existing WordPress assertions; eight JavaScript checks; six actual scoring-service HTTP checks; PHP/JS syntax and archive integrity. Counts exclude repeated baseline assertions.
9. **Exhausted:** PASS. Zero candidates finalizes exhausted and dispatches Business immediately. An actual three-category HTTP run drained Sports → Business → AI with WP-Cron disabled, without an administrator request between workers.
10. **Failed:** PASS. A thrown processing exception marks failed, frees the slot and claims Business. A legacy active-batch conflict becomes blocked and also starts Business. Cancelled and skipped scheduled jobs cannot freeze the queue.
11. **Concurrency 1:** PASS. Only one slot is claimed; subsequent categories start on predecessor completion. Duplicate triggers and token replay do not start duplicate workers. Two article chunks preserve the same run ID, reach exactly the two-Draft limit, then dispatch Business.
12. **Concurrency 2:** PASS in the controlled WordPress harness. Technology remains held as a valid processing worker; Sports completes, and Business takes its slot immediately while Technology remains active. AI stays waiting. This is a controlled interleaving test, not simultaneous production MySQL/PHP load testing.
13. **Six-hour retry:** PASS. A blocked RSS response schedules its independent source retry for approximately +21600 seconds; the current category becomes exhausted, releases its slot, and Business starts. Removing the source cancels the pending retry; a stale delivered retry checks current configuration again and cannot requeue a removed source.
14. **Draft-only:** PASS. Generated fixtures, including successful multi-chunk queue runs, remain `draft`. No automatic publishing was added. Existing scoring and manual publishing remain available.

## RSS root cause and diagnostics

The code audit found two concrete stale-configuration paths: Run All did not save edited category fields before execution, and Source URL HTML discovery automatically followed advertised RSS feeds even when the RSS field was empty. The RSS parser itself also followed HTML feed links. No hardcoded TOI feed or legacy RSS merge was found. Production database values were not inspected, so this report does not claim which path produced that particular live notice.

All group-run category saves now finish before enqueue, including explicit empty RSS values. Workers read current saved settings and validate each configured source before fetching. HTML source discovery no longer promotes advertised RSS into configured feeds. Pending source retries contain only category/type/URL, validate current saved configuration, and are cancelled on removal. Source tests report zero configured/tested RSS and SKIPPED when RSS is empty. Controlled TOI-like HTML plus an old blocked-feed cache confirms the removed advertised feed is not fetched or reported as current RSS.

HTTP diagnostics distinguish actual fetch status/content type, skipped/not-fetched states, parse outcome and candidate count. Blocked-source reports preserve reason and next retry time. Provider secrets and worker tokens are excluded from UI/debug output.

## Validation environment and limits

Isolated WordPress 7.1, PHP 8.4.25, SQLite, Rank Math Free 1.0.278. External provider calls are controlled fixtures. Existing regression suites: scoped settings/images/links 61, shared saves/source testing 32, foundation 28, security 27, pipeline/media 120, distinct non-image SEO 30 = 298. New queue/RSS suite adds 47 = 345. JavaScript has two existing error-status and six queue/save/poll checks. Scoring service has six HTTP tests using the real analyzer. Total 359 automated assertions, plus the local HTTP/browser exercise.

The HTTP exercise ran the real admin-ajax worker endpoint on the disposable WordPress server with `DISABLE_WP_CRON=true`. Logs showed three sequential worker requests; all jobs were exhausted before any browser inspection. Browser Run Selected and polling were also exercised. Test categories/settings/cron were restored afterwards. No production website, paid API or MilesWeb behavior was tested.

Normal immediate handoff needs working same-site HTTP loopback. If the host refuses it, the plugin logs the failure and retains cron fallback. A disabled or traffic-starved cron cannot recover blocked loopback on its own; configure a real host cron in that situation. Claims are database conditional updates/unique option keys, but simultaneous production MySQL stress testing remains outside this validation.

Tests under tools/tests are for the disposable harness and must not run against a production database.
